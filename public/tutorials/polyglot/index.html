不同的语言，
如何运行在同一个程序里？

你已经能写 add(20, 22)。现在换一个问题：如果 add 的实现来自另一种语言，C++ 还可以调用它吗？

一个项目可能既要调用成熟的库，又要做界面、统计和高效计算。不同部分选用合适的语言，是为了复用已有成果、减少开发工作；收益值得时，才增加语言之间的边界。

下面从这个动机出发，把编译、链接和二进制接口连成一条线，最后亲手做出一个输出 42 的混合语言程序。

开始探索 →
C++ 主程序
main.cppadd(20, 22);
C 函数实现
add.creturn a + b;
./demo输出：42

先分清：多种语言，怎样协作？

不同进程：消息通信

前端 JavaScript⇄ HTTP ⇄后端 Python

各自运行，把请求和结果序列化后传递。双方无需使用同一种语言，也不需要被链接成同一个程序。

同一进程：函数调用

C++ 主程序→ 调用 →C / Rust 库

代码被编译为兼容的目标文件或库，在同一进程内调用。接口两侧需要对齐符号、类型和调用约定。

这页会带你走过：函数在哪里实现 → 源码如何变成目标文件 → 链接器如何找到实现 → 跨语言调用还需要遵守什么约定。示例默认你见过变量、函数和简单 C++ 代码；不要求先学汇编。

为什么目标文件还不能直接运行？因为它可能还引用着别处的函数，地址也尚需安排。对常规本机 C 程序，链接器还需要结合其他目标文件、库和启动所需组件，形成可被系统加载的程序。

这些命令，分别在哪儿停下？

选项做到哪一步典型输出

这是对符号解析的简化演示，假定符号名、目标格式、架构和 ABI 均兼容。真实错误文案依链接器而异。

链接器还会处理重定位：根据最终布局修正需要调整的位置。链接能解决“引用指向哪里”，但它不会自动修复“调用双方对参数的理解不一致”。后者留到 ABI 章节。

库里的代码，怎么进入程序？

“库”是便于复用的一组代码。下面两种方式描述库与程序的组合关系；它们都可以参与多语言项目。

program A
包含所需的库代码
program B
包含所需的库代码
共享库 · libmath.so / .dylib / .dll

链接时，所需库代码被纳入各自的程序。通常更便于打包这一部分依赖，但多个程序可能重复包含同一份库代码。

动态链接并不等于“整个库只占一份内存”。兼容进程可共享某些只读代码页，各进程仍有自己的地址空间和运行时状态。共享库通常在程序加载时被加载，也可以按需显式加载；不是每调用一次函数都重新读取磁盘。
常见平台静态库共享库
Linux.a.so
macOS.a.dylib
Windows / MSVC.lib.dll，常配合导入库

这些是常见命名，扩展名不是语言。Windows 的 .lib 也可能是导入库，不能仅凭后缀断定库代码被静态打进了程序。共享库的更新还必须考虑 ABI 兼容性。

C 实现，C++ 调用。

我们把入口和输出留在 C++，把加法放在 C。两边共享一份头文件，各自编译，再链接成一个程序。这个例子故意使用简单整数，先把接口和构建过程看清。

共同的声明 · 两种语言都能包含
#ifndef ADD_H
#define ADD_H

#ifdef __cplusplus
extern "C" {
#endif

int add(int a, int b);

#ifdef __cplusplus
}
#endif

#endif
#include "add.h"

int add(int a, int b) {
    return a + b;
}
#include <iostream>
#include "add.h"

int main() {
    std::cout << add(20, 22) << '\n';
    return 0;
}
  1. 把三个文件放在同一个文件夹。头文件提供声明，add.c 提供实现，main.cpp 使用这个接口。
  2. 分别交给对应的语言编译器。cc 编译 C，c++ 编译 C++，都用 -c 暂停在目标文件。
  3. 让 C++ 编译器驱动完成最后链接。它会按本机工具链的配置处理 C++ 标准库等依赖。仅把 add.o 加入链接，不会让整个项目变成 C 项目。
终端命令（Linux / macOS）
cc -std=c11 -Wall -Wextra -c add.c -o add.o
c++ -std=c++17 -Wall -Wextra -c main.cpp -o main.o
c++ main.o add.o -o demo
./demo
预期输出：42
extern "C" 到底做了什么？在 C++ 一侧，它为相关函数指定 C 语言链接；在常见工具链中，这也避免使用 C++ 的函数名修饰方式。__cplusplus 条件让 C 编译器跳过这段 C++ 专用语法。它不会把任意 C++ 类型或代码“转换成 C”，也不能消除架构、数据布局等兼容要求。[2]
如果去掉 extern "C"，为什么可能链接失败？

C++ 支持函数重载，常见实现会把参数等信息编码进链接时的符号名；而 C 编译出的 add 使用另一套命名约定。若 C++ 一侧按 C++ 链接寻找它，就可能找不到 C 一侧提供的定义。

这不是“加个 extern 就什么都兼容”：接口类型、平台 ABI、对象格式和编译目标仍要匹配。std::string、异常和对象所有权等也需要单独设计，不能照搬这个整数例子。

进阶：如果把实现换成 Rust？

原理仍然是导出兼容的接口，再用适合目标平台的方式构建、链接库。下面展示 Rust 2024 的接口片段，使用 C 的整数类型和调用约定；此片段不是本页下载示例的一部分。[3]

// 使用 Rust 2024 edition
use std::ffi::c_int;

// SAFETY: 整个链接单元中，add 符号只有这一个定义。
#[unsafe(no_mangle)]
pub extern "C" fn add(a: c_int, b: c_int) -> c_int {
    a + b  // 本教程只使用 20、22 这样不会溢出的输入。
}

extern "C" 指定 ABI；no_mangle 保留可预测的导出符号名。Rust 2024 要求将这一属性标为 unsafe(...)，因为符号名冲突可能带来安全问题。真实接口还要约定溢出、错误处理和所有权；不要让异常或 Rust panic 随意跨过 FFI 边界。具体链接参数依平台、库类型和工具链而异。

运行环境：Linux/macOS，已安装支持上述选项的 C/C++ 工具链。Windows/MSVC 的命令和产物命名不同。这是终端练习，网页中的实验不会代替真实编译器。

进入 ABI 实验 →

找到函数，还不等于调对函数。

假设函数已经找到了：调用方把第一个参数放到 R0，函数却从 R1 读。这时，符号能对上，计算依然可能出错。要让二进制代码正确协作，双方还需要遵守兼容的 ABI。

ABI · 二进制接口类型如何布局、参数如何传递、结果从哪里取、符号如何命名？调用双方按同一套底层规则传递两个整数

调用方把 20、22 放入 R0、R1；被调函数从同样的位置读取，求和后返回到 R0。调用方读回 42，与预期一致。

教学模型：R0/R1/R2 是虚构处理器的寄存器，R2 初始固定为 7；4096、8192 是模拟地址。这不是 x86、ARM 或任何实际平台 ABI。输入限定为 −99～99 的整数，避免把溢出问题混进本实验。

ABI 通常还管哪些事情？

数据的表示与布局

类型大小、对齐要求、结构体字段布局等。同样写成“一个整数”，二进制表示也需要双方理解一致。

参数、返回值与栈

参数在寄存器还是栈上、返回值放哪里、哪些寄存器需要保存、谁负责相应的栈操作。

符号如何导出和查找

函数名如何编码、哪些符号可见。链接器能找到函数，是跨语言调用的必要环节之一。

目标平台的规则

处理器、操作系统、对象格式、编译器选项等都会影响兼容性。“都是 C ABI”不能跨所有平台通用。

接口相同，不代表 ABI 相同。源码里都写 add(a, b)，不能证明二进制兼容；同样，某次恰好得到正确数值，也不能证明约定一致。跨语言接口还要明确内存归谁释放、字符串如何编码、错误如何传递。

真实 ABI 通常由具体平台规范定义。例如 Arm AArch64 过程调用标准会规定真实的寄存器与参数传递规则；本页的虚构实验只用于帮助理解“约定必须对齐”。

选择与自检 →

为什么混用，什么时候值得？

多语言本身不是目标。先明确需要复用的能力，以及接口要跨过哪条边界，再衡量构建、调试和维护的成本。

复用已有库和系统能力

已有成熟 C 库，或操作系统提供了 C 接口。通过合适的接口接入，能减少重复实现。

把热点放到合适的位置

先测量瓶颈，再考虑用原生代码处理关键计算。频繁跨边界、复制数据，也可能抵消收益。

兼顾开发效率与底层控制

界面、脚本和业务逻辑可以使用合适的生态；硬件、实时约束或特定平台能力另作设计。

逐步迁移旧系统

保留已有模块，通过稳定接口替换局部。团队经验、平台支持也会影响选择，但会增加协调成本。

先按协作边界做选择

不同机器，独立部署→ 消息 / 网络接口

例如 HTTP、RPC。重点设计协议、序列化、超时和错误语义。

同一进程，复用本地库→ FFI / 原生接口

先确认支持的语言接口、目标平台 ABI、类型、内存与错误处理约定。

已有单语言方案足够→ 保持现有方案

只有收益足以覆盖构建、调试和分发成本时，再增加语言边界。

把几个词放回正确的位置

Compiler / 编译器
把源码转换到目标表示的工具；日常“编译命令”还可能驱动多个阶段。
Object file / 目标文件
包含机器码、符号和重定位等信息，供后续链接使用。
Linker / 链接器
组合目标文件与库，解析符号引用并处理重定位等工作。
Library / 库
被其他代码复用的代码集合，可通过静态或动态方式参与程序。
API / 应用程序接口
代码或系统向使用方提供的功能与使用约定，不等同于二进制兼容性。
ABI / 应用程序二进制接口
二进制组件协作的底层规则，与具体平台和工具链相关。
FFI / 外部函数接口
一种语言调用另一种语言实现的函数时使用的机制。
IPC / 进程间通信
独立进程之间交换数据与消息的方式，网络通信是相关形态之一。
